1. Project Overview

MedSecure AI is an AI-powered healthcare platform. It helps users understand symptoms, medical reports, prescriptions, appointments, and basic health data in simple language.

The project is built as a full-stack web application. The frontend gives a modern user interface. The backend handles authentication, database operations, file uploads, AI requests, and secure APIs. MongoDB stores users, reports, chat history, diagnoses, appointments, and medications.

Simple explanation: A patient can login, upload a prescription, ask health questions, get AI-assisted guidance, see dashboard statistics, and manage appointments from one place.

3. End-To-End Workflows

Signup and Login Workflow

  1. User enters name, email, and password in the frontend.
  2. Frontend sends data to POST /api/v1/auth/signup.
  3. Backend validates the data using Zod.
  4. Backend checks if email already exists.
  5. Password is hashed using bcrypt.
  6. OTP is generated and email verification data is saved.
  7. User logs in through POST /api/v1/auth/login.
  8. Backend returns JWT tokens and user information.
  9. Frontend stores token in localStorage and uses it for protected requests.

Prescription Analyzer Workflow

  1. User opens the Prescription Analyzer page.
  2. User uploads an image or PDF.
  3. Frontend creates FormData with field name image.
  4. Axios sends request to POST /api/v1/predictions/analyze-prescription.
  5. JWT middleware verifies the user.
  6. Multer reads the uploaded file from memory.
  7. Backend sends base64 image data to Gemini model candidates.
  8. AI returns structured JSON.
  9. Frontend displays patient details, summary, problem, medicines, referral, urgency, and metrics.

AI Chat Workflow

  1. User writes a health question or uploads a file.
  2. Backend fetches recent chat history for context.
  3. Backend builds a patient-friendly prompt.
  4. It tries Gemini first, OpenAI second, and mock local fallback last.
  5. Response and doctor recommendation are returned.
  6. Conversation is saved in MongoDB ChatHistory.

Why JavaScript Is A Good Choice Here

  • Same language on both sides: The frontend and backend both use JavaScript, so development is easier.
  • JSON-friendly: Healthcare records, API responses, and AI outputs are naturally represented as JSON objects.
  • Fast development: React, Next.js, Express, Mongoose, Axios, and many packages are available.
  • Good for real-time and API work: Node.js handles many network requests efficiently.
  • Large community: Errors are easier to solve because documentation and examples are widely available.
  • Easy deployment: Next.js frontend can go to Vercel/Netlify, and Express backend can go to Render/Railway/VPS.

11. Main Code Snippets And Explanation

JWT Protected Route Middleware

File: backend/src/middleware/auth.js

export const requireAuth = (req, _res, next) => {
  const authHeader = req.headers.authorization || "";
  const token = authHeader.startsWith("Bearer ") ? authHeader.slice(7) : null;

  if (!token) {
    throw new ApiError(StatusCodes.UNAUTHORIZED, "Authentication required");
  }

  try {
    const decoded = verifyAccessToken(token);
    req.user = decoded;
    next();
  } catch (error) {
    throw new ApiError(StatusCodes.UNAUTHORIZED, "Invalid or expired token");
  }
};

This middleware protects private APIs. It checks the Authorization header, verifies the JWT, stores the decoded user in req.user, and blocks invalid users.

User Password Hashing

File: backend/src/models/User.js

UserSchema.pre("save", async function encryptPassword(next) {
  if (!this.isModified("password")) return next();
  this.password = await bcrypt.hash(this.password, 12);
  next();
});

UserSchema.methods.comparePassword = function comparePassword(candidatePassword) {
  return bcrypt.compare(candidatePassword, this.password);
};

The project never stores plain passwords. Before saving, bcrypt converts the password into a secure hash. During login, bcrypt compares the entered password with the stored hash.

12. Security And Validation

  • Password hashing: bcrypt hashes passwords before storing them.
  • JWT authentication: protected routes require a valid token.
  • Role checks: admin-only routes use role middleware.
  • Validation: Zod validates important request payloads.
  • Security headers: Helmet adds safer HTTP headers.
  • File upload handling: Multer processes uploaded reports and images.
  • Database fallback: local mock fallback allows development when DB is not available.
  • AI fallback: if one AI provider/model fails, the app can use another model or mock result.

13. Interview Questions And Answers

Q1. What is MedSecure AI?

MedSecure AI is a healthcare web platform that helps patients manage medical information, ask health questions, upload reports or prescriptions, receive AI-assisted explanations, book appointments, and view health dashboard data.

Q2. What problem does it solve?

Many patients do not understand reports, symptoms, medicines, or which doctor to visit. The project gives simple explanations and organizes patient data in one secure place.

Q3. What is the architecture?

It is a monorepo with a Next.js frontend and a Node.js Express backend. MongoDB stores data. AI providers such as Gemini and OpenAI provide analysis, with local fallback logic when AI is unavailable.

Q4. Why did you use JavaScript?

JavaScript can run in both browser and backend. This helps build the full stack with one main language, reducing context switching and making development faster.

Q5. Why use Next.js?

Next.js gives file-based routing, React UI, fast builds, server/client rendering options, good developer experience, and easy deployment to Vercel.

Q6. Why use React?

React makes the UI component-based. Components like Header, ProtectedRoute, Button, Card, Dashboard widgets, and Analyzer views can be reused and maintained easily.

Q7. Why use Node.js and Express?

Node.js is good for API servers that handle many I/O operations. Express is lightweight and makes routing, middleware, and REST API design simple.

Q8. Why use MongoDB?

Medical app data such as users, reports, chat messages, diagnoses, and appointments can vary in shape. MongoDB stores JSON-like documents, which match JavaScript objects well.

Q9. Why use Mongoose?

Mongoose adds schemas, validation, relationships, hooks, and easier database methods on top of MongoDB.

Q10. Why use JWT?

JWT allows stateless authentication. The backend can verify the token without storing a server-side session for every request.

Q11. How is password security handled?

Passwords are hashed with bcrypt before saving. The plain password is never stored in MongoDB.

Q12. What is role-based access control?

Users have roles such as patient, doctor, and admin. Middleware checks roles before allowing sensitive actions such as admin analytics or listing all users.

Q13. How does signup work?

The user sends name, email, and password. Backend validates input, checks duplicate email, hashes password, generates OTP, stores the user, and sends verification email if SMTP is configured.

Q14. How does login work?

The backend finds the user by email, compares the password with bcrypt, creates access and refresh tokens, and sends user details plus tokens to the frontend.

Q15. How is protected routing done in frontend?

ProtectedRoute checks auth state. If no user is logged in, it redirects the user to login and preserves the current route as a redirect target.

Q16. How does the chatbot work?

The user sends a message or file. Backend fetches recent chat context, builds a patient-friendly prompt, tries Gemini, then OpenAI, then a local mock response. It saves the conversation.

Q17. Why keep chat history?

History gives context to future answers and allows users to review previous health discussions.

Q18. How does prescription analysis work?

The frontend uploads an image or PDF as FormData. Backend uses Multer to read the file, sends image data to Gemini, expects structured JSON, and returns patient details, summary, medicines, urgency, and referral.

Q19. What happens if Gemini fails?

The controller tries model candidates such as gemini-2.0-flash and gemini-2.5-flash. If all fail, it returns a mock fallback result so the UI does not crash.

Q20. How does symptom prediction work?

The backend validates symptoms, calls an AI prediction service, and if it fails searches a local Symptom2Disease dataset to estimate disease, risk score, precautions, and specialist.

Q21. What is the local illness dataset used for?

It gives offline educational triage support. It is not a final diagnosis engine, but it allows the app to give basic guidance even without external AI.

Q22. How does dashboard work?

The dashboard API fetches recent chats, recent diagnoses, recent reports, active medications, and count statistics for the logged-in patient.

Q23. How are appointments handled?

Patients create appointments with doctorId, scheduled date, and reason. Listing logic changes based on role: patient sees own appointments, doctor sees assigned appointments, admin can see all.

Q24. How are reports handled?

Multer stores uploaded reports in the uploads folder. MongoDB stores metadata such as filename, URL, MIME type, patientId, and uploader.

Q25. What is the role of Zod?

Zod validates request bodies. It prevents bad data from entering controllers and database logic.

Q26. What is the role of Helmet?

Helmet adds common HTTP security headers to reduce web vulnerabilities.

Q27. What is the role of CORS?

CORS allows the frontend domain to call the backend API safely.

Q28. What is the role of Morgan?

Morgan logs HTTP requests during development and production debugging.

Q29. What is the role of Multer?

Multer handles multipart file uploads for reports, chat attachments, and prescription analysis.

Q30. How does frontend state management work?

React state manages local UI. TanStack Query manages server data fetching, caching, loading, and mutation states.

Q31. Why use Axios?

Axios gives a clean API client with base URL, interceptors, JSON handling, and FormData support.

Q32. How is multilingual support done?

The frontend uses i18next and react-i18next. UI text is stored as translation resources and users can switch language.

Q33. What are the main collections?

Users, Diagnoses, ChatHistory, Appointments, Reports, and Medications.

Q34. How do you prevent route not found errors?

Routes are centralized in backend route modules, frontend API base URL is controlled, and analyzer aliases are registered inside the predictions router.

Q35. What is the biggest strength of the project?

It combines practical patient workflows with AI explanation, secure auth, real database storage, and fallback behavior.

Q36. What is a limitation?

AI output is not a final medical diagnosis. It needs doctor review, stronger clinical validation, and production-grade monitoring before real clinical use.

Q37. How would you scale this project?

Use managed MongoDB, object storage for files, queue-based AI processing, caching, monitoring, rate limiting, audit logs, and separate AI microservices.

Q38. How would you improve security?

Add refresh-token rotation, rate limiting, audit logs, encrypted file storage, stricter CORS, HTTPS-only cookies, input sanitization, and HIPAA-style access controls.

Q39. Why did you choose a monorepo structure?

A monorepo keeps frontend and backend in one repository. This is helpful for a student or small team project because setup, version control, and feature coordination become easier. A change in the API and a matching frontend change can be committed together.

Q40. What are the main folders in the project?

The frontend folder contains the Next.js UI, pages, components, hooks, services, and translations. The backend folder contains Express app setup, routes, controllers, models, middleware, services, config, and scripts.

Q41. Explain the backend folder structure.

Routes define API URLs, controllers contain business logic, models define MongoDB schemas, middleware handles auth/errors, services contain reusable AI or local NLP logic, and config handles environment and database connection.

Q42. Explain the frontend folder structure.

The app folder contains Next.js pages and layouts. The src/components folder contains reusable UI and layout components. The src/services folder contains API calls. The src/context folder stores auth state. The src/lib folder contains translations.

Q43. What is REST API?

REST API is an architectural style where frontend and backend communicate using HTTP methods like GET, POST, PUT, PATCH, and DELETE. In this project, APIs like /auth/login, /predictions, and /chatbot follow REST-style design.

Q44. Why use controllers instead of writing all logic in routes?

Controllers keep route files clean. Routes only define the URL and middleware. Controllers handle validation, database operations, AI calls, and responses. This makes the backend easier to read and maintain.

Q45. What is middleware in Express?

Middleware is a function that runs between request and response. In this project, middleware is used for authentication, role checking, JSON parsing, file upload, CORS, logging, error handling, and not-found handling.

Q46. What is the purpose of app.js?

app.js creates the Express app, applies middleware such as helmet, cors, morgan, json parser, cookie parser, static uploads, API routes, not-found handler, and error handler.

Q47. What is the purpose of server.js?

server.js starts the application. It connects to MongoDB first, then starts the Express server on the configured port. It also handles unexpected errors during development.

Q48. How does environment configuration work?

The backend uses dotenv to load variables from .env. The env.js file centralizes important values such as PORT, MONGO_URI, JWT secrets, client URLs, and OAuth credentials.

Q49. Why should secrets be stored in .env?

Secrets such as database URL, JWT secret, API keys, and SMTP password should not be hardcoded because they are sensitive. .env allows separate local and production configuration.

Q50. What is MONGO_URI?

MONGO_URI is the MongoDB connection string. It tells Mongoose where the database is hosted, which database to use, and how to authenticate.

Q51. What DNS problem did you solve in MongoDB connection?

MongoDB Atlas SRV URLs require DNS SRV lookup. Some networks block or fail this lookup. The project now resolves SRV records explicitly and then passes a direct seed-list URI to Mongoose, improving connection reliability.

Q52. What happens if MongoDB is unavailable in development?

The backend can start in degraded mode if ALLOW_START_WITHOUT_DB is true. Some controllers use in-memory fallback data so the app remains testable during development.

Q53. Why is fallback important in this project?

Fallback improves user experience and development reliability. If AI or database temporarily fails, the app can still show basic guidance instead of crashing completely.

Q54. What is the difference between authentication and authorization?

Authentication checks who the user is, usually through login and JWT. Authorization checks what the user is allowed to do, such as admin-only analytics or patient-specific records.

Q55. How does role-based authorization work here?

The user role is stored in the JWT payload and user model. Middleware allowRoles checks whether req.user.role is included in the allowed roles before continuing.

Q56. Why is password select:false used in the User model?

select:false prevents password hashes from being returned by default in database queries. This reduces accidental exposure of sensitive password data.

Q57. Why is email indexed and unique?

Email is used for login and must identify one user only. Unique prevents duplicate accounts, and index improves lookup speed during login.

Q58. What are timestamps in Mongoose schemas?

timestamps: true automatically adds createdAt and updatedAt fields. These help sort reports, chats, appointments, and diagnoses by time.

Q59. What are references in MongoDB models?

Fields like patientId and doctorId refer to User document IDs. This creates relationships between collections while still using MongoDB documents.

Q60. What is the Diagnosis model used for?

It stores patient symptom prediction results, including symptoms, predicted disease, confidence, risk score, precautions, recommended specialist, and model version.

Q61. What is the ChatHistory model used for?

It stores a userId and an array of messages. Each message has role, text, and timestamp. This allows users to review previous AI conversations.

Q62. What is the Appointment model used for?

It stores patientId, doctorId, scheduledAt, status, reason, and notes. It supports patient booking and doctor/admin appointment viewing.

Q63. What is the Report model used for?

It stores metadata for uploaded medical reports, such as original filename, storage URL, MIME type, patient ID, and uploader ID.

Q64. What is the Medication model used for?

It stores medicine name, dosage, frequency, time of day, active status, and optional source report. The dashboard can show active medications.

Q65. How does the frontend send a protected request?

The Axios interceptor reads medsecure_access_token from localStorage and adds it as Authorization: Bearer token. The backend requireAuth middleware verifies it.

Q66. How does the frontend handle file uploads?

The UI creates FormData and appends the selected file. The API client removes manual Content-Type so the browser can set the correct multipart boundary.

Q67. Why should we not manually set multipart Content-Type?

When sending FormData, the browser must include a boundary in Content-Type. If we manually set it incorrectly, the backend may not parse the file.

Q68. How does TanStack Query help this project?

It manages loading states, errors, caching, refetching, and mutations. This makes dashboard, appointments, predictions, and analytics easier to build.

Q69. What is useMutation used for?

useMutation is used for actions that change data, such as login, signup, creating appointments, sending chatbot messages, and uploading prescriptions.

Q70. What is useQuery used for?

useQuery is used for reading data from the backend, such as dashboard stats, appointment list, prediction list, chat history, and analytics.

Q71. Why use ProtectedRoute in frontend?

ProtectedRoute prevents private pages from displaying to unauthenticated users. It improves UX by redirecting users to login with a helpful message.

Q72. How does the dashboard collect data?

The frontend calls /dashboard/stats. The backend fetches recent chats, diagnoses, reports, active medications, and counts using Promise.all for parallel database queries.

Q73. Why use Promise.all in dashboard controller?

Promise.all runs independent database queries at the same time. This reduces total response time compared to waiting for each query one by one.

Q74. How does admin analytics work?

The admin route counts total users, patients, doctors, appointments, and predictions. It is protected by requireAuth and allowRoles('admin').

Q75. How does the local illness search work?

The localNlpService compares user symptoms with records in localIllnessDataset and returns matched illness, category, risk level, next steps, and score.

Q76. Why is the local dataset not a final diagnosis?

The dataset is a simple educational symptom association reference. Real diagnosis needs doctor examination, medical history, lab tests, and clinical judgment.

Q77. How does AI prompt engineering appear in the project?

The chatbot builds a structured patient-friendly prompt that asks the AI to use simple language, explain step by step, avoid final diagnosis, and include urgent warning signs.

Q78. Why does the chatbot use conversation history?

Recent history helps the AI understand context. For example, if the user asked about fever earlier, the next question can be answered with that context.

Q79. How is doctor recommendation generated?

The backend checks keywords such as chest pain, breathing, fever, anemia, headache, skin, eye, and stomach problems. It maps them to suitable specialists and urgency messages.

Q80. What is the difference between chatbot and prescription analyzer?

The chatbot is conversational and accepts questions or attachments. The prescription analyzer is document-focused and returns structured JSON fields such as patient details, medicines, summary, referral, and urgency.

Q81. Why did you add multiple Gemini model candidates?

AI providers may retire or restrict model names. A candidate list lets the backend try another supported model automatically, improving reliability.

Q82. What happens when AI returns invalid JSON?

The JSON parsing fails, the controller catches the error, logs it, and returns a fallback result. In production, better JSON repair and stricter schema validation could be added.

Q83. Why is the AI medical response limited?

AI can make mistakes and should not replace clinical judgment. The app intentionally uses disclaimers and avoids final diagnosis or exact medicine decisions.

Q84. How would you make AI output safer?

Use strict JSON schema validation, medical safety filters, source citations, doctor approval workflow, confidence display, audit logs, and clear emergency warnings.

Q85. What is CORS and why is it needed?

CORS controls which frontend origins can call the backend. It is needed because frontend and backend may run on different domains or ports.

Q86. What is Helmet and why is it used?

Helmet sets secure HTTP headers, helping protect against common web attacks such as clickjacking and MIME sniffing.

Q87. What is cookie-parser used for?

cookie-parser reads cookies from requests. Even though the current token flow mainly uses localStorage, cookie-parser supports future cookie-based auth.

Q88. What is morgan used for?

Morgan logs HTTP requests. During development, it helps debug which routes are being called and what status codes are returned.

Q89. What is express-async-errors?

It allows thrown errors inside async Express controllers to be passed to the error handler without manually wrapping every controller in try-catch.

Q90. How does the global error handler help?

It creates consistent error responses. Instead of crashing or returning raw stack traces, it sends a structured JSON response with success false and message.

Q91. How does the not-found handler help?

It catches unknown routes and returns a clear message like Route not found: POST /api/v1/..., which helps debugging frontend-backend mismatch.

Q92. What was the prescription route issue and how was it fixed?

The frontend was hitting a deployed API that did not contain the local route. The local API client was changed to use localhost in development, and analyzer routes were centralized in the predictions router.

Q93. How would you debug a 404 API problem?

Check frontend API base URL, check backend route registration, call the route directly with curl/Postman, inspect server logs, verify method and path, and ensure the running backend is the updated code.

Q94. How would you debug a 401 problem?

Check whether the request includes Authorization Bearer token, whether the token is expired, whether JWT secret matches backend, and whether frontend localStorage contains the correct token.

Q95. How would you debug a file upload problem?

Check field name, FormData creation, Content-Type boundary, multer route configuration, file size limits, and backend req.file value.

Q96. What are possible production deployment platforms?

Frontend can be deployed on Vercel or Netlify. Backend can be deployed on Render, Railway, or a VPS. MongoDB Atlas can host the database.

Q97. What environment variables are needed in production?

Backend needs MONGO_URI, JWT secrets, SMTP values, AI API keys, CLIENT_URL, and ALLOW_START_WITHOUT_DB=false. Frontend needs NEXT_PUBLIC_API_URL pointing to the production backend.

Q98. Why should ALLOW_START_WITHOUT_DB be false in production?

In production, users expect real data persistence. Starting without DB could lead to missing records or degraded behavior, so production should fail loudly if DB is unavailable.

Q99. How would you store uploaded reports in production?

Instead of local uploads folder, use secure object storage such as AWS S3, Cloudinary, or Azure Blob Storage with private access and signed URLs.

Q100. What privacy concerns exist in this project?

Medical reports, chat history, prescriptions, and symptoms are sensitive. They need encryption, strict access control, audit logs, minimal data collection, and secure storage.

Q101. What healthcare compliance improvements are needed?

For real-world healthcare use, the project would need HIPAA-like controls, consent management, audit trails, encryption at rest, access logs, data retention policy, and clinical validation.

Q102. How would you add refresh token rotation?

Store refresh tokens securely, issue short-lived access tokens, rotate refresh tokens on use, invalidate old tokens, and detect token reuse.

Q103. How would you add rate limiting?

Use middleware such as express-rate-limit to limit requests per IP/user, especially for login, signup, AI chat, and file upload routes.

Q104. How would you add tests?

Q105. Which test cases are most important?

Auth login/signup, protected route access, invalid token handling, prescription upload, chatbot fallback, prediction creation, dashboard stats, admin role protection, and database connection failure.

Q106. What is the difference between unit, integration, and end-to-end tests?

Unit tests check small functions. Integration tests check multiple modules together, such as API plus database. End-to-end tests check full user flows from browser to backend.

Q107. How would you improve code quality?

Add TypeScript, stronger schemas, tests, linting in CI, consistent error handling, reusable constants, API documentation, and smaller service modules.

Q108. Why might TypeScript be useful?

TypeScript adds type safety. It can catch mistakes in API response shapes, component props, controller payloads, and model fields before runtime.

Q116. What is the difference between localStorage token and HTTP-only cookie token?

localStorage is easy to use but more exposed to XSS. HTTP-only cookies are not readable by JavaScript and are generally safer when combined with CSRF protection.

Q117. Why is API base URL important?

If the frontend points to the wrong API base URL, it may call an old deployed backend or wrong port, causing 404, CORS, or auth errors.
